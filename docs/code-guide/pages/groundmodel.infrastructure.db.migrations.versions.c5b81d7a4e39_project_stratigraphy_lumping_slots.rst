.. CG-EXPLANATION-START id=module-header

**What this does.** A migration that adds three columns to the ``project`` table: two JSONB slots holding the manual lumping map and one big-integer revision counter. JSONB is PostgreSQL's binary JSON column type. The header carries its revision id and the id it follows.

**Why it is here.** The docstring explains the lumping map (built via Fill from boreholes then Apply) previously lived only in the desktop's memory and was lost on a crash between Apply and Save. The two slots mirror the two-stage save model: ``staged`` is the durable copy of the live edit, ``saved`` is what the last File then Save committed, and their difference is the unsaved-changes signal. The third column is a monotonic revision counter (one that only ever counts up) written to both the database and the crash-recovery file, so recovery compares revisions, never wall-clocks (see docs/design/autosave-recovery.md). It is hand-written, not autogenerated, because autogeneration would also propose unrelated, harmful schema drift.

.. CG-EXPLANATION-START id=function:upgrade

**What this does.** Adds the two nullable JSONB columns and the nullable big-integer revision counter to ``project``.

**Why it is here.** All three are nullable with no default so no-lumping-map-yet (empty) stays distinct from staged-once-at-revision-0. The counter is big-integer because it only ever grows over the project's whole life.
