# Clean / dirty / undo — app-wide audit

**Status:** audit only, nothing changed. Read from source on `develop` @ `097afb8c0`,
2026-08-01. No runtime reproduction, no DB writes.

**The rule being audited** (owner, arrived at during the geotech stage, to be applied
app-wide):

1. Anything the PROGRAM generated and the user has not accepted is **dirty** — the system
   may regenerate or delete it freely.
2. Anything the user has **accepted** is **clean** — the system never deletes it.
3. The user's own explicit delete still removes anything, clean or not.
4. Destructive user actions should be undoable.

The geotech stage failed all four. The question this audit answers is: **where else?**

---

## 0. Read this first — the geotech bug is not fixed, only half-fixed

The prompt describes the geotech failure in the past tense. It is still live, and the
verification is exact:

`derive_geotech_edges_from_litho` takes the acceptance flags as **defaulted keyword
arguments**:

```python
# src/groundmodel/application/geotech_edge_derivation.py:242-243
    user_approved: bool = True,
    source: str = "manual",
```

Two callers:

| Caller | Passes the flags? | Result |
|---|---|---|
| `auto_correlate_geotech_edges.py:234-235` | **Yes** — `user_approved=False, source=AUTO_SOURCE` (`"auto"`) | correct: suggestions |
| `subdivide_all_bodies.py:606-616` | **No** — falls through to the defaults | **every SAB-derived edge is stamped `user_approved=True, source='manual'`** |

`SubdivideAllBodies` is the bulk generator. Its own module docstring states the outcome
as if it were intended (`subdivide_all_bodies.py:65`: *"All edges are `user_approved=True`,
`source='manual'`"*). So the 217 all-manual edges measured on the owner's model are what
the primary geotech path still produces today; only the standalone Auto-correlate verb was
corrected.

And the thing that consumes them does not filter:

```python
# src/groundmodel/application/subdivide_all_bodies.py:680-684  (_delete_all_geotech_data)
delete(LithoContactCorrelationEdgeOrm).where(
    LithoContactCorrelationEdgeOrm.model_id == geotech_model_id,
)
```

No `user_approved` predicate. Re-running Subdivide deletes every geotech edge — the
program's own and the engineer's hand-drawn packing ties alike. The `ReSubdivideConfirmDialog`
warns honestly, which is why this has been survivable; but the flag that would let the
code *keep* the hand-made ones exists, is populated with a constant, and is then ignored
anyway.

## 2. The gaps, ranked by what work can actually be lost

Ranked by consequence to the owner, not by ease of fix. An hour of hand correlation
outranks a regenerable cache.

### 2.1 — Dedupe: one click, no confirmation, no undo, and the code believes otherwise

`useGeologicalModelOps.ts:339-342` states:

> `NOT in the undo stack — this is an explicit "clean up old data" action with a
> confirmation dialog, not an interactive edit.`

**That dialog was never built.** `GeologyToolbar.tsx:362-375` wires
`onClick={() => void handleDedupe()}` straight through, and `handleDedupe` (:212-220)
calls the API ungated.

**Concretely:** pressing **Dedupe** on the Geology toolbar, once, immediately DB-deletes
formation contacts with no dialog and no undo. The dedupe is provenance-aware in the
engineer's favour (`deduplicate_formation_contacts.py:161-172` ranks `manual_pick` above
`interpolated` above `borehole_observation`), so it will not sacrifice a hand pick to an
auto one. But the third tie-break is `created_at` descending — **so where an engineer has
two hand-placed picks on the same (anchor, formation), the older one is deleted.**

The backend already returns `removed_contact_ids` and its docstring says they exist *"so
a future undo command could re-create them"*. The safety net is designed, returned over
the wire, and dropped on the floor.

*Correction to the surveys:* one asserted flatly that "the discarded ones are the
engineer's own picks". That over-states it — the rank protects manual picks against auto
ones. The real exposure is manual-vs-manual.

### 2.2 — The close-without-save dialog promises the opposite of what it does

`UnsavedChangesDialog.tsx:43`:

> "The metadata editor has unsaved edits. If you discard, your typed values will be lost;
> **the database row stays as it was**."

Behind it, `handleUnsavedDiscard` (`useProjectLifecycle.ts:419-433`) performs a full DB
replace-restore of the entire project from the `.gmproj`. And `attemptClose` (:354-371)
opens this dialog whenever `projectDirty`, which is
`metadataDirty ‖ hasUnsavedMutations ‖ any sessionImport set` (:235-243) — i.e. for **all**
session work in every stage.

**Concretely:** after an afternoon of correlating in the Sections stage with no File→Save,
closing the project and pressing **Discard** reverts every correlation, every boundary
drag and every accepted suggestion — behind a sentence that explicitly promises the
database is untouched. This is the single most destructive gesture in the app, and it is
labelled with the smallest possible loss.

### 2.3 — Two "restore" undos that restore less than the user will believe

* **Delete contact.** The revert re-creates the layer with a **new id**
  (`useContactCrud.ts:1099-1130`) and restores **none** of the correlation edges that
  cascaded with it (`litho_contact_correlation_edge_orm.py:155,160`). *Concretely:*
  deleting a contact that carried five approved manual ties and pressing Ctrl+Z brings the
  boundary back and leaves all five ties gone — permanently, with the boundary visibly
  restored so nothing looks wrong.
* **Delete cross-section.** The revert re-POSTs an equivalent section with a new id
  (`useSections.ts:653-658`). Every correlation edge authored on that section cascaded via
  `section_id ON DELETE CASCADE` (`:140`) and is not restored.

The dialog in front of the second one is **wrong in both directions in one sentence**
(`SectionsToolbar.tsx:1543-1544`): *"Formation contacts placed on it are also removed"* —
they are not; `formation_contact` has no cross-section FK (verified: no `section_id` /
`cross_section` column in `formation_contact_orm.py`). What IS cascade-deleted is every
correlation edge on the section, approved manual ties included, and the dialog never
mentions them. The backend route docstring carries the same stale belief
(`cross_section.py:405-406`: *"today there's nothing to cascade"*).

The same sentence also ends **"This cannot be undone"** — about an action that pushes an
undo entry. `DeleteContactConfirmDialog.tsx:43` does the same. Alarming-and-wrong is how
users are trained to click through dialogs that are right.

### 2.4 — A body's name is bound to a depth rank, not to the rock (new finding — neither survey established this)

Naming a body is the app's **only** accept-marker for bodies —
`NameBodyDialog.tsx:90-92` and `SectionsCanvas.tsx:971-973` both say a named body survives
the detector reconcile and the bulk lens delete. The resolver honours it
(`resolve_litho_instances_use_case.py:242-244` skips orphan-deletion when `body.name`).

But body identity is `(formation_id, body_ordinal)` — the DB unique constraint is
`uq_body_model_formation_ordinal` (`body_orm.py:57-63`) and the reconcile keys on exactly
that (`resolve_litho_instances_use_case.py:210-211`). And **the ordinal is a positional
depth rank, reassigned from scratch on every resolver run**:

```python
# src/groundmodel/domain/services/resolve_litho_instances.py:286-292
for _gk, comps in group_to_comps.items():
    comps.sort(key=lambda triple: triple[0])   # shallowest component first
    for ordinal, (_rep_key, comp, rep) in enumerate(comps):
```

`enumerate` over depth-sorted connected components, per soil-code naming group.

**Concretely:** name a sand body "Channel Sand A" (it is ordinal 2). Later draw a
correlation that creates a new, shallower sand component. Ordinals renumber; the old
ordinal-2 rock is now ordinal 3. On the next resolver run the reconcile looks up
`(formation_id, 2)`, finds the existing row — the one carrying "Channel Sand A" — and
reuses it for a **physically different body**. The name is never deleted, so nothing warns;
it simply now labels the wrong rock. Symmetrically, a named body whose ordinal disappears
survives as a detached row with no members, because :242 preserves it.

**Confidence:** established from the code by construction (ordinal assignment, the unique
constraint, and the reconcile lookup are all verified above). **Not reproduced at runtime** —
I did not drive a correlation change and observe a name move. This is the highest-value
thing in the report to confirm with a live repro before acting on it.

### 2.5 — Two DB deletes that never set the dirty flag, so even the discard net misses them

`markMutated()` is what makes a mutation recoverable via close-without-save. Three
destructive verbs skip it:

* **Reset manual points** (`SectionsToolbar.tsx:400-423`) — DELETEs every hand-drawn
  boundary shape model-wide. This is the purest "user-authored, program-deleted" verb in
  the app. It has a correct ConfirmDialog and **no undo**; without `markMutated` the
  close-without-save revert never engages either. *Concretely:* pressing it destroys every
  free-draw lens shape in the project, and there is no path back short of reopening the
  last-saved `.gmproj` — which nothing prompts you to do, because the project does not
  look dirty.
* **Dissolve body** (`SectionsCanvas.tsx:1001-1016`) — same, behind a native
  `window.confirm`, and it can delete a **named** (accepted) body.
* **Propagate admixtures** (`SectionsCanvas.tsx:364-400`) — bulk-overwrites user-entered
  composition on every unit in a connected component. No confirm, no undo, no
  `markMutated`, and the blast radius appears only in the success toast afterwards.

### 2.6 — Divide boreholes: no confirmation on a verb that cascades hand-drawn ties

`SectionsToolbar.tsx:1237-1258` fires on click. `divide_boreholes.py:346-353` deletes every
prior borehole geotech layer, and `layer_a_id`/`layer_b_id ON DELETE CASCADE`
(`litho_contact_correlation_edge_orm.py:155,160`) takes every packing tie attached to those
bands with it.

**Concretely:** after hand-connecting packing bands across a borehole, clicking **Divide
boreholes** once destroys those ties with no dialog, no undo, and a tooltip that mentions
only re-dividing to match. The bands themselves are legitimately dirty (hand edits are
refused on boreholes, `geotech_band_edit_helpers.py:168-181`); the ties are not.

*Correction to the surveys:* one cited `geotech_borehole_materialiser.py:160-161` as the
delete. That is wrong — those lines re-activate an inactive geotech model; the file contains
no delete at all. The real site is `divide_boreholes.py:346-353`.

### 2.7 — The undo path launders review state

Both uncorrelate reverts and the geotech disconnect revert call `createContactCorrelation`,
which hardcodes `source:'manual'` (`geology.ts:564`); the server then forces
`user_approved=True` (`correlate_litho_contacts.py:307-316`).

**Concretely:** delete an unapproved auto suggestion, press Ctrl+Z, and it returns as an
**approved manual** edge — permanently indistinguishable from one you drew. The drag-retarget
path documents this promotion as deliberate (`useEdgeDragRetarget.ts:311-312`); on the undo
path it is silent and unintended.

### 2.8 — Every review state has a bulk accept and none has a bulk reject

Verified: `grep -rn "Reject all\|rejectAll"` across `desktop/src/renderer/src` returns
**nothing**. What exists is Accept all / Accept all (bulk) (`SectionsToolbar.tsx:925-966`),
Accept correlations (geotech, :1310-1324), Confirm all (absences,
`InspectLensBodyPanel.tsx:295-330`).

There are bulk *clears* — "Clear", "Clear bulk", "Clear correlation suggestions" — but a
clear is not a reject: it dismisses without recording the judgement, so the next Suggest
regenerates the same proposal. The asymmetry pushes toward accepting sweeps that have not
been reviewed, which is precisely how generated rows stop being distinguishable from
hand-made ones. That is the geotech failure arriving by a second route.

### 2.9 — `docs/ux.md` grants permission for all of this

## 3. The pattern

**The geotech failure was not a missing flag. It was a flag that existed, was correctly
typed, was correctly rendered — and was written as a constant by the code that mattered.**

`user_approved` and `source` are on `litho_contact_correlation_edge` for both models. The
overlay reads them axis-agnostically (`CorrelationEdgesOverlay.tsx:755`). The litho side
populates them truthfully — 298 auto / 182 manual. The geotech side's bulk generator passes
neither argument and takes the defaults `user_approved=True, source='manual'`
(`geotech_edge_derivation.py:242-243`, called bare at `subdivide_all_bodies.py:606-616`).
Nothing was missing. One caller declined to say what it was doing, and everything
downstream believed it.

**Four other artefacts share that exact shape** — a provenance or acceptance signal that
exists and is defeated:

1. **Geotech NAD bands** (row 5). `source` is `'segmenter'` vs `'manual'` and *is* truthful
   in the DB — this is the honest one. It is defeated at the **render**: every band draws
   identically, and `countGeotechHandEdits` has exactly one consumer app-wide, inside a
   dialog. A flag nobody can see is a flag nobody trusts.
2. **Litho layers** (row 6). `source` is truthful when written, then **overwritten by a
   drag** — `useContactCrud.ts:362-363` stamps `'manual'` on any boundary move, so the
   segmenter's own output launders itself into hand-made through ordinary use. Same failure
   as geotech, one column over, arriving gradually instead of at once.
3. **Correlation edges on the undo path** (§2.7). The flag is honest at creation and
   **destroyed by the revert**, because the only create-edge client hardcodes
   `source:'manual'` (`geology.ts:564`). Ctrl+Z is a laundering machine.
4. **Body names** (§2.4). Here the acceptance signal is not a column at all — naming *is*
   the accept gesture — and it is bound to `body_ordinal`, a positional depth rank
   recomputed by `enumerate` on every resolver run
   (`resolve_litho_instances.py:286-292`). Storing an acceptance marker against something
   the program renumbers is the same class of mistake as writing the flag constant: the
   signal survives, but it stops meaning what it said.

The generalisable rule: **wherever the program can write a provenance value, check that
every writer passes it explicitly, that a reader renders it, and that the key it hangs on
is not something the program regenerates.** Defaulted keyword arguments on a shared
derivation helper (`user_approved: bool = True`) are the specific hazard — they make the
dishonest call site look identical to the honest one.

A second, independent pattern worth naming: **`markMutated` is the app's last safety net,
and three destructive verbs skip it** (§2.5). Undo is the first net, the confirmation
dialog the second, `markMutated` + discard the third. Reset manual points has only the
second; propagate admixtures has none.

## 4. What already conforms

So this reads as a map, not an indictment — these are safe and several are worth copying:

* **Formation absences** (row 10) are the reference implementation. Explicit per-row source
  badge, Confirm offered only on `inferred` rows, and a tooltip that states the consequence
  in the user's terms: *"the inference engine will no longer overwrite this row"*
  (`InspectLensBodyPanel.tsx:481-503`). The engine overwrites `inferred` and leaves `manual`
  alone. This is exactly the rule.
* **Hidden investigations** (row 15) fully match the documented contract — project-local
  hide, never a DB delete, demoted-not-removed rendering, and a working
  "N removed · restore all" path (`useInvestigationData.ts:117-180`; `docs/ux.md:129-140`).
* **Litho correlation edges** (row 3) are the clean/dirty mechanism working as designed:
  auto writes unapproved, manual writes approved, the render distinguishes them at a glance,
  Accept appears only while pending, and **Clear suggestions respects acceptance
  server-side** (`contact_correlations.py:429-434` filters `user_approved.is_(False)`).
* **Two dialogs are the template.**
  `shell/stages/geology/FormationSelectionDialog.tsx:727-762` computes the exact
  formations-and-contacts loss, renders the warning only when non-zero, flips the confirm to
  `danger`, and moves `autoFocus` to Cancel **only when there is something to lose**.
  `ReSubdivideConfirmDialog.tsx:80-89` does the same with `handEditCount` and separates the
  two kinds of loss because they weigh differently — a connection can be re-derived by
  Auto-correlate, a hand-placed boundary cannot.
* **Tie suggestions** (row 11) are the only generated type with the full
  accept / reject / accept-all / clear quartet, and they never touch the DB until accepted.
* **Virtuele Boring** (row 14) is correct by construction — informative overlay, no accept
  path, no way to promote a prediction into the model.
* **Derived 3D output is correctly exempt.** Voxel solids and TIN surfaces have no undo and
  need none. **Verified**: a Build cannot destroy user-authored body names or colours —
  `_delete_orphans` (`litho_solid_persistence.py:379-420`) deletes only `LithoBodySolidOrm`
  rows.
* **Litho ghost rendering** (row 7) reads correctly: pending wears a 45° hatch, accepted
  layers hide so the committed band stands alone
  (`LithoSuggestionGhostColumns.tsx:648-670,:775-782`). The problem there is lifecycle, not
  legibility.
* **Litho contacts have the best undo coverage in the app** — eight distinct push sites
  across move / create / delete / batch / seed / accept.
